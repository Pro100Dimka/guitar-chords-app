# Chord-recognition evaluation protocol

The user's Behind Blue Eyes chart is an evaluation reference. The recognizer
receives decoded PCM only. Song names, expected keys, chord sequences, section
positions and reference labels must not enter its features or decoder. The
reference JSON and evaluation scripts are development tools, not app assets.

## Frozen comparison

The baseline is commit `01ddfeab9ba5aa0c8a794f4a1a84f617260a3a1b`, whose
`chords.rs` SHA-256 is
`1ac850955a73da198ee5cb87c9158c23371913f19d2666b0e3eaa0a594181345`.
Baseline outputs are generated by the actual production Rust core, not a second
implementation of its scoring logic. Candidate source, model and executable
hashes must be recorded before evaluating the additional twelve recordings.

The original development take is GuitarSet `00_SS3-98-C_comp`. The twelve other
takes in [the pinned manifest](offline-chord-quality-fixtures.json) were selected
before inspecting their baseline or candidate scores. They cover six players,
five performance styles and three shared progressions, totaling about 379.08
seconds. They are twelve recordings, not twelve unrelated songs or full-band
mixes. Two takes with previously reported annotation timing problems are
excluded explicitly in the manifest.

Those twelve recordings were held out **from decoder tuning for the first
frozen candidate only**. The first evaluation then revealed two mechanisms that
lost a played third: a hard event gate and whole-span averaging. They informed a
narrow follow-up fix, so the original twelve are now explicitly
**development-after-evaluation**. Their original results are preserved in
[candidate 1](offline-chord-evaluation/candidate-1/README.md), including every
regression. They cannot support a second blind-evaluation claim.

A [fresh twelve-recording selection](offline-chord-evaluation/fresh-holdout/README.md)
was sealed before acquisition or inference, excluding all previously used
recordings and the same two known timing exclusions. It totals 367.9884 seconds,
with two takes in different styles per player. The deterministic ranking,
selection constraints and all media/annotation/PCM hashes are preserved. Only
one frozen follow-up candidate is evaluated on it; both the baseline and the
candidate run on all twelve. Results are reported separately from the original
development cohort. No take is removed or replaced after seeing its result.

These are holdouts from the current decoder development. Basic Pitch
was trained using GuitarSet, and the published checkpoint has no verified
track-membership manifest available here. Its current upstream preparation code
shuffles track IDs and allows an unspecified split seed. Consequently these
recordings cannot establish performance on audio unseen during pretrained-model
training. This caveat applies even if the decoder is frozen before evaluation.
See the pinned upstream [split configuration](https://github.com/spotify/basic-pitch/blob/fa5997af0a8210982619003269994a1be25eddf3/basic_pitch/data/commandline.py)
and [GuitarSet preparation](https://github.com/spotify/basic-pitch/blob/fa5997af0a8210982619003269994a1be25eddf3/basic_pitch/data/datasets/guitarset.py).

## What the scores mean

GuitarSet supplies two chord annotations. **Instructed** labels describe the
chord sheet. **Performed** labels are sheet-informed, semi-automatic annotations
derived from the individual string notes, with manual verification. Report both
independently; neither should silently replace the other after seeing results.

| Metric | Match rule | Important limit |
| --- | --- | --- |
| Exact root and formula | Same enharmonic root and relative pitch-class set, duration weighted | Added and omitted notes remain distinct; slash bass is ignored |
| Root only | Same enharmonic root, duration weighted | A wrong major/minor or suspension can still score correctly |
| Major/minor projection | Same root and complete unambiguous major/minor triad | Non-triad reference duration is excluded and reported separately |
| Pitch-class Jaccard | Intersection divided by union of absolute pitch classes | Equal pitch sets can have different roots and chord meanings |

Examples: `C9` and `Cadd9` differ by the dominant seventh; `Csus2` and `Gsus4`
share pitch classes but have different roots. The evaluator preserves these
distinctions. It also preserves explicitly omitted notes in performed labels.
There is no substitution of a forgiving interior-only score for the full
timeline score.

Reference `X` means unknown and is excluded with its duration reported.
Reference `N` is evaluated as no chord; it matches predicted `N` only. Missing
prediction intervals count wrong. Overlaps, nonfinite times and unsupported
label syntax cause an error rather than disappearing from the denominator.

The selected takes contain substantial major/minor material, some sevenths and
unusual performed formulas, but little clean suspended/add-tone material. A
single aggregate score therefore does not establish equal accuracy for every
supported chord family. Synthetic controls provide additional coverage of
voicings, transpositions and transitions; they do not replace real recordings.

## Behind Blue Eyes reference

[The chord-only reference](offline-chord-behind-blue-eyes-reference.json)
preserves the user's original notation and order without lyrics. In this chart:

| User notation | Canonical comparison label |
| --- | --- |
| `D5(9)` | `Dsus2` |
| `A5(9)` | `Asus2` |
| `C9` | `Cadd9`, only for this reference |

The last interpretation is supported by the original-version intro printed on
page 10 of the [DUX publisher preview](https://dux-verlag.de/ancora_myfactory/CustomUpload/374O357O340O370O356O369O350O352O365O354O366O369O352O/D%20873_01.%20Behind%20Blue%20Eyes.pdf).
The following pages use simplified voicings; they are not an exact timed
transcription of this recording. The app's general chord editor retains the
ordinary dominant-ninth meaning of `C9`.

The reference contains no timestamps. In particular, exact `E`/`Esus4` switch
times and the instrumental repeat count are not established. Sequence
comparison reports event insertions, deletions and substitutions for both the
printed structure and a separately identified two-cycle instrumental
hypothesis. Neither is chosen afterward merely because its score is better.
These edit counts are **not full-song chord accuracy**. Predicted timestamps are
reported as predictions, not converted into reference boundaries.

The input is the complete 276.4568-second alternative music-video audio
identified in the existing provenance files. It is not the 30-second Apple
preview, nor a claim about every album/live version. Music audio is not bundled
with the app or committed to the repository.

## Reproduction

Keep downloaded media outside the repository:

```sh
python3 scripts/evaluate-offline-chords-extended.py self-test
python3 scripts/fetch-offline-chord-quality-fixtures.py \
  --output-dir /tmp/freetune-chord-quality --decode
python3 scripts/evaluate-offline-chords-extended.py compare \
  --selection docs/offline-chord-quality-fixtures.json \
  --annotations /tmp/freetune-chord-quality/annotations \
  --baseline /tmp/freetune-chord-baseline \
  --candidate /tmp/freetune-chord-candidate \
  --output /tmp/freetune-chord-comparison.json
python3 scripts/evaluate-offline-chords-extended.py sequence \
  /tmp/freetune-chord-candidate/behind-blue-eyes.json \
  docs/offline-chord-behind-blue-eyes-reference.json
```

The comparison directories contain one production-core JSON result per track,
named `<track>.json`. The downloader verifies pinned source sizes and SHA-256s
before decoding. The report hashes both prediction files and annotations.
If evaluation results are subsequently used to tune the decoder, disclose that
reuse and obtain a fresh set before making another holdout claim. The original
twelve have already made this transition, as described above. Repeating their
commands is reproduction or development validation, not a new blind test.

Core timings start with decoded PCM. Decode, file-provider access and UI time
must be measured separately. Workstation timings and stripped native-library
sizes are not measurements of phone latency, installed size or store download
size.
