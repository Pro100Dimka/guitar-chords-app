# FreeTune: сохранённое состояние доработки и проверки

**Состояние на 13 ноября 2026: работа не завершена.** Среда выполнения стала недоступна после основного прогона и во время проверки инструментальных записей.

Этот коммит сохраняет только отчёт и наблюдённые измерения. **Изменения реализации приложения/backend из рабочей среды в него не входят.** Исходники этой ветки остаются на уровне `3a73101fb22483b405e61f1c3ce340709f8cc1da`, кроме двух файлов данного контрольного отчёта. Публичный сервер не развёрнут, APK не собирался, проверки на физическом Android не проводились.

## Почему кандидат не принят

Обработаны все 30 полных вокальных записей: 20 английских, 5 украинских, 5 русских. Все задания завершились, но успешное выполнение процесса не означает правильную расшифровку.

| Показатель | Исходный small | Проверенный кандидат turbo с новым адаптером |
|---|---:|---:|
| WER на EN20, 6237 слов эталона | 36,19% (2257 ошибок) | 28,35% (1768 ошибок) |
| WER на десяти английских heldout-записях | 36,76% | 32,68% |
| WER с отдельным учётом маркеров неизвестных слов | 37,26% | 29,08% |
| Точные слова с доступными временными метками, из 5693 | 3853 — 67,68% | 2819 — 49,52% |
| MAE начала/конца на одних и тех же 2284 словах | 0,360 / 0,340 с | 0,302 / 0,274 с |

Из 20 английских песен 18 улучшились по WER и две ухудшились. Kinematic — 25,79% → 31,45%; Explosive Ear Candy «Like The Sun» — 45,07% → 57,04%. На английском heldout точность границ немного ухудшилась: начало 0,39465 → 0,39740 с, конец 0,37469 → 0,37605 с. 284 из 769 строк EN теперь имеют только приблизительное время строки. Снижение среднего MAE нельзя выдавать за улучшение всей синхронизации при уменьшившемся покрытии.

При сравнении двух адаптеров на одинаковых исходных сегментах turbo WER уменьшился с 33,01% до 28,35%, но выявлен серьёзный дефект сохранения гипотез. У Explosive Ear Candy «Like The Sun» число верных слов осталось 255, а вставки выросли с 0 до 72; один приблизительный фрагмент 171,44–192,92 с содержит 111 повторений одного токена. Слабое/повторяющееся окно нельзя считать надёжным только из-за высоких оценок отдельных слов.

**Инструментальный контроль не пройден.** Последнее подтверждённое состояние — завершены 7 из запланированных 10 GuitarSet-фрагментов; все семь получили по одной лишней строке и одному лексическому слову. Исходный small не выдавал текста на всех десяти. Примеры нового вывода: `… you.` и `… solo`. Это видимая регрессия. Нативная проверка шла с turbo в два потока, чтобы соответствовать прежнему GuitarSet-прогону; конфигурация общего сервера использует четыре. Эту разницу необходимо исследовать, а не использовать для снятия обнаруженного дефекта.

Для UK/RU нет проверенных человеком текстов и временных границ именно этих исполнений. Их WER равен `null`; точность аккордов полных вокальных песен не измерена ни для одного языка. В украинском примере «Східна мелодія» сохранена сомнительная строка 27,18–29,98 с «Дякую за перегляд!», похожая на выдуманную служебную подпись.

## Что было реализовано и проверено локально

- Автоматический доступ установки к общему сервису; в обычном интерфейсе нет ввода IP или токена. Пока адрес выпуска пуст, доступность разбора явно отключена.
- Согласие на отправку полной записи, объявленные ограничения, позиция очереди, ожидание `Retry-After`, повтор получения того же задания после краткого сбоя связи, отмена.
- Разделение файлов/заданий/ключей повторов по установкам; случайные 256-битные доступы, на сервере сохраняются хеши; постоянные квоты и отдельный бюджет отмены.
- Очистка загруженного/декодированного аудио после обработки, обработка ошибок удаления и восстановления сервера; ограниченное хранение результата.
- Docker/Compose/Caddy и инструкции оператора. Caddyfile проверен официальным бинарным файлом, Compose — схемой; контейнеры и публичный TLS не запускались.
- Сохранение старой библиотеки, ручной и автоматической версий, защиты ревизий и повторов; резервные копии не содержат доступ к сервису. Аудио переносится отдельно с привязкой по SHA-256.
- Три локализации, сообщения о приблизительном времени строки, работа с фактической позицией существующего проигрывателя. Нативное воспроизведение на устройстве не проверялось.

Проверки до отключения: 14 Jest-наборов / 134 теста, реальная SQLite, TypeScript и ESLint — успешно. Полный backend-прогон: 67 тестов; позже добавлены и проверены два новых случая оценщика (69 различных проверок суммарно). Ещё 14 тестов независимого scorer прошли. Это проверка кода и контрактов, не доказательство качества на телефоне.

## Аккорды и ресурсы

На десяти инструментальных GuitarSet-фрагментах устранение принудительного стартового `N` длиной 20 мс уменьшило лишние смены 23 → 13. Полный аккорд: 43,5508% → 43,5923%; трезвучная основа: 65,4094% → 65,4591%; F1 смен в пределах ±0,5 с: 74,1379% → 81,1321%. Пропущенных смен осталось семь, MAE сопоставленных границ — 0,1138 с. Это небольшое исправление начального перехода, а не доказательство точной гармонии вокальных песен.

Полный вокальный корпус содержит 6175,24 с аудио. Проверка использовала два отдельных процесса по четыре потока на Linux CPU; время серии — 1466,07 с, сумма времени отдельных заданий — 2863,32 с, максимум RSS одного worker — 2496,95 МиБ. Эти конкурентные времена нельзя сравнивать как ускорение с прежним последовательным HTTP-прогоном.

В последовательном контролируемом сравнении четырёх development-песен с одинаковым новым адаптером и seed 0: small → turbo дал WER 30,04% → 23,14%, время 299,046 → 396,063 с и пик RSS 1802,15 → 2499,79 МиБ. Этот первоначальный выбор кандидата позднее не прошёл инструментальный контроль. Окончательный профиль сервиса ещё не принят.

## Методика и пределы доказательств

Разделы development16 и heldout14 были зафиксированы до итогового распознавания. Английские baseline-результаты и две славянские записи уже были известны: это перспективное сравнение изменений, а не исторически незнакомый корпус. После обнаружения текущих ошибок данные считаются просмотренными для следующей корректировки; их нельзя повторно объявлять независимым heldout.

Эталоны Jam-ALT/JamendoLyrics использовались только при оценке, не подавались в распознавание. Сравнение старого small с новым кандидатом одновременно меняет модель, адаптер и случайное зерно; отдельный опыт на одинаковых нативных сегментах помогает выделить изменение адаптера. Четыре контроля совпали с отдельными запусками старого адаптера по всему тексту, времени и confidence. Ресурсы для несуществующего второго инференса не приписывались.

## Продолжение после восстановления доступа

1. Сначала сохранить и проверить рабочие изменения, отчёты и состояние процессов. Не делать `reset --hard`, не заменять рабочую копию клоном и не повторять завершённые прогоны поверх результатов.
2. Снять реальные нативные/исходные временные гипотезы на ошибочных инструментальных файлах для small и turbo, сопоставив число потоков, no-speech, logprob, повторяемость и слова нулевой длины.
3. Проверить общие консервативные правила, без списков фраз конкретных песен: сохранить прежнюю осторожность при `compression_ratio > 2.4`; не превращать отсутствие пригодных нативных временных опор в утверждаемый текст. Это пока гипотезы исправления, а не сделанная правка.
4. Повторить оценку исправленного кандидата, явно указав просмотренные данные и объём новой независимой проверки. Пройти инструментальный контроль и настоящий shared HTTP smoke.
5. Проверить настоящим валидатором приложения все окончательные результаты, обновить профиль/документы, опубликовать полный diff реализации и сохранить принятые примеры.

Для обычного пользовательского запуска отдельно нужен действующий сервер разработчика с HTTPS. Для доказательства работы на Android — физическое устройство. APK по текущему заданию собирать не нужно.
